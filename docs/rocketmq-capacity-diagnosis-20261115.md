# RocketMQ 事务消息重构：容量探索与瓶颈诊断（2026-11-14～15）

> **后续复测说明：** 本报告的「240 RPS 为最高已验证稳定档」只针对当时的 RocketMQ Broker 1GiB、5奖品实验条件。后续将专用 Broker 内存配额调至2GiB后，5奖品270 RPS已通过，5奖品300 RPS仍出现积压；50奖品300 RPS通过。热点行锁对照、失败实验及独立发送异常详见 [后续根因实验报告](rocketmq-rootcause-experiments-20261115.md)。不同环境结果不能直接作为同条件吞吐提升比例。

> 本地真实压测证据。当前测试版本：`9b74b82`，分支 `codex/rocketmq-transactional-20261114`。所有数据来自本机实际 JMeter、SQL/资源采样和最终业务对账；未使用模拟的性能数字。

## 一、背景与实验口径

目标是在此前 RocketMQ 150 RPS 持续通过的基础上，确定可持续业务吞吐边界，观察超限时哪个环节首先积压，并做单变量优化验证。历史文档中 222 RPS 属于先前实现，不能直接视为当前 RocketMQ 分支的容量上限，也不可据此宣称同环境同比增长。

Apple M4 单机，JMeter 5.6.3（72 线程），应用宿主机运行，MySQL 8.0.46（2 CPU / 2 GiB）、Redis 7.2.16、RocketMQ 5.3.4（单 Broker 2 CPU / 1 GiB、同步刷盘）在独立 Docker Compose 项目 `lottery-rocketmq-perf` 运行。MySQL 开启事务日志与 Binlog 同步刷盘。固定到达速率、每档不同活动 ID、5 种等概率奖品、100% 命中；应用实际执行参加次数扣减、Redis 库存预扣、RocketMQ 事务消息、MySQL 库存结算与本地发奖。为了测量核心链路，**仅本地压测启动器关闭入口准入限流**；此结果不代表默认生产限流配置的对外可达吞吐。各轮测试的用户数、时长及 JMX 见各自 `parameters.json`、`command.json` 和 `plan.jmx`。

区分两类口径：`HTTP RPS` 是接口完成请求数，`库存结算吞吐` 是异步库存完成数；只有错误率、异步积压趋势、完成延迟、入口停止后排空和逐笔业务对账同时过门槛，才能称为**持续稳定**。仓库 `doc/performance/check_stability.py` 要求测量窗口至少 180 秒、HTTP P99 小于 1 秒、异步 P95 上界小于 10 秒、15 秒内排空、首尾平均待发奖积压增长不超过 1 秒的吞吐等。

## 三、单变量诊断与优化

**观察：入口快，库存结算慢。** 480 RPS、原始 4 消费线程时，HTTP 仍能以约 480 RPS 完成且零错误，但库存实际只完成约 314 笔/秒，待发奖积压持续增长。发奖消费组 Lag 很低，库存消费组 Lag 高达 18,417。仅凭 HTTP 成功率会遗漏此故障。

**实验 A：提高数据库 CPU 并无显著收益。** 将隔离测试 MySQL CPU 限额临时从 2 提到 4（代码和其他测试参数保持不变），库存完成速率仅从 314.40 变为 315.19/s，积压依然显著，不能将瓶颈简单归因于 MySQL CPU 配额。实验后 CPU 上限已恢复 2。

**实验 B：消费线程 4→8，短时吞吐显著提升。** `RocketMqConsumers` 通过 `lottery.rocketmq.consumer-threads` 设置两个消费组的线程数，原始默认 4；RocketMQ 两个 Topic 均有 8 队列。在 480 RPS、相同 JMeter 负载下，把应用启动参数设为 `--lottery.rocketmq.consumer-threads=8`，库存完成速率 314.40→459.86/s，提升 **46.3%**；库存 Lag 峰值 18,417→3,822；库存 P95 延迟上界 48.43→7.56 秒；入口停止后排空 51.83→7.04 秒。HTTP P99 则 68→87 ms。**只是短时性能显著改善，480 RPS 仍未通过完整稳定性门槛，不应说“480 RPS 稳定”。**

**进一步发现：共享奖品库存行和数据库事务竞争。** 库存消费者调用 `StockSettlementListener.onMessage`，经 `ActivityPrizeRepository.settleAwardStock` 先写唯一结算账本，再对 `activity_prize` 的对应奖品库存执行条件 UPDATE；事务成功后再推进订单库存状态并触发发奖。MySQL `performance_schema.data_lock_waits` 实际抓到 `lottery.activity_prize` 的 `uk_activity_award` 索引上的 X 行锁等待。在 8 线程、440 RPS、190 秒测量的长时测试中，InnoDB 新增 23,212 次行锁等待、累计约 174.7 秒等待，库存结算降至约 320/s，库存 Lag 峰值 22,047。270 RPS 持续档位也累计约 16,968 次行锁等待、161 秒等待。更多消费并发提高了入库并发，同时加剧了对五种奖品库存行的争用。数据库 COMMIT 与订单状态 UPDATE 同样有显著累计耗时，热点行不能被当成唯一原因。

**环境归因边界。** 同一 Docker Broker 在多轮测量中保持运行、积累消息/文件缓存；其 1 GiB 内存限制多次接近上限。cgroup 内存明细包含可回收文件缓存；未观察到 OOM Kill。未单独控制 Broker 缓存/存储状态，因此无法把长时失速完全归因于数据库热点行，更不能排除 Broker 内存/同步刷盘及宿主背景负载的影响。所有结论仅适用于这套资源配额和单机实验条件。

## 四、工程后续与面试口径

已验证的低风险优化是**调整消费并发配置**，无需改动事务消息和幂等逻辑。此次调整仅通过本地测试进程启动参数实施，**没有修改生产默认的 4 线程配置，也没有宣称生产部署上线**。建议先对照测试 4/8 线程的相同 180～240 RPS 长时窗口，并重启或隔离 Broker、固定资源采样，再决定是否提交默认线程配置变更。

若继续突破持续容量，优先对热点奖品库存条件 UPDATE 的锁等待、事务边界和 COMMIT 耗时增加阶段性计时，区分锁竞争与刷盘/同步提交开销；再考虑减少热行竞争、减少无意义事务边界或合理批处理结算账本与库存，但必须保留事务消息回查、Ledger 幂等、Redis/MySQL 对账和异常补偿。不能仅提高线程数/连接池或简单删除事务。

**可直接口述的面试回答：**“我对 RocketMQ 事务消息抽奖链路做了逐级压测，发现 480 RPS 时 HTTP 虽然零错误，但库存消费者只能处理约 314 单每秒，消息持续积压，说明接口吞吐掩盖了异步瓶颈。我先做 MySQL CPU 对照，发现加 CPU 基本没用；随后检查消费配置，发现 8 个队列只有 4 个消费线程。将线程数调到 8 后，相同短时负载下库存结算吞吐提升约 46%，排空时间由 52 秒降到 7 秒。进一步长时间加压发现，库存行锁竞争使高负载仍不能持续稳定。最终基于包含业务对账与异步积压的验收门槛，确认本机约 240 RPS 持续稳定，270 RPS 尚不达标；后续要优化的是数据库库存热点和事务开销。”
