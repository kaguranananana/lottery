# Lottery 单库、限流与实时 Outbox 实测

2026-11-11 至 11-12，Asia/Shanghai。JMeter 5.6.3 和应用运行在同一台 10 核、16 GiB 的 Apple Silicon 主机。独立 Docker 栈使用 MySQL 8.0.46、Redis 7.2.16 和 Kafka 2.8.1，MySQL 限 2 CPU/2 GiB。应用和 JMeter 使用 JDK 17，交付 WAR 使用 Java 8 构建。V7 压测复用了隔离库和原中间件资源配置，每轮使用新的活动、用户和库存。

## 改造与验证

- 八张业务表共用一个 MySQL 库和一个 Hikari 池。V6 旁路复制为分片自增 ID 重新编号，保留请求号、参与号、订单号和历史账本。真实 MySQL 验证跨片订单、请求和归属冲突回滚。V7 在隔离库保留了 159,917 笔既有订单。 [单库部署与迁移](single-database.md)
- HTTP 以 Servlet Principal 匹配请求用户，先获取本机许可，再用 Redis Lua 同时检查全局与用户活动令牌桶。默认全局 100 RPS、突发 32，每用户活动 2 RPS、突发 3，本机并发 24。429 分别标识全局、用户和并发拒绝，准入 Redis 故障返回 503。相同请求号经准入后可回放原结果。 [HTTP 契约](../.trellis/spec/backend/http-contract.md)
- Spring 三个独立固定延迟任务默认每 10 秒运行，活动只扫描到期状态。TX2 提交后把库存义务交给有界工作池。库存账本与条件扣减仍同事务，库存完成时持久登记发奖义务。两种消息独立记录重试时间与代数，发送失败退避，发送超时或进程退出按租期恢复，迟到回调无法覆盖新代数或终态。 [V7、重试与对账](outbox-delivery.md)
- 移除了库存和发奖的固定值 Redis 标记。HTTP 短锁继续使用所有者令牌，真实 Redis 验证旧执行者不能清除新标记。发奖事实与消息终态由同一条 CAS SQL 写入，BLOCKED 经人工对账后递增代数再释放。计划发奖字段保留历史快照与回放语义。
- Java 8 构建通过，默认测试 52 项。完整独立中间件回归 77 项；补充事务回滚和 Redis 所有权验证后复跑 32 项；最终调参后复跑 41 项，均无失败或跳过。覆盖同请求回放、并发扣次、库存预扣、账本幂等、Kafka 停机重启、消费者重新分配、回调代数、BLOCKED 恢复和索引扫描。
- 独立进程在 TX2 提交后、Kafka 发送前收到 SIGKILL，停机前库存投递代数为 0，账本不存在。重启后实际 Spring 调度恢复三项终态，账本一条，重放同一订单，个人额度只扣一次。活动从 PASS 自动启动、预热并到期关闭。

## 压测闭环与容量

- 初版实时 Outbox 在 350 突发档触发 348 次资源拒绝，库存 P99 上界 10,097 ms。日志显示两个补偿任务同时提交候选，数据库领取和回调写入均占用工作线程。补偿改为最多使用四分之一在途许可，并按实测 SQL 等待将工作线程从 4 调至 6。同负载复测资源拒绝 61 次，补偿额度拒绝 1 次，库存 P99 上界 498 ms，停压库存待结算 0 笔。
- 150 RPS 不限流短测复测，资源拒绝由 705 次变为 1626 次，库存 P95 上界由 2,537 ms 变为 144,141 ms，停压时仍有 1,414 笔库存待结算，排空耗时 149.53 秒。短测未通过异步 P95 小于 10 秒、停压后 15 秒内排空两项前置门槛，持续测降至 120 RPS。同档启用限流完成 100.1 笔/秒，429 为 33.3%。开关两组连接池等待峰值分别为 0 和 6。
- 不限流 150 RPS 的压力同时落在数据库和投递链路。MySQL 平均使用约 1.52 个核，连接池用满 48 个连接，仍有 1,626 次实时投递因容量转入补偿，库存 Kafka Lag 峰值 843。默认限流的同档对照中，池无等待、补偿候选为 0、库存 Lag 峰值 5。
- 中间单库版本由一秒扫描投递。40 RPS 同场景用旧账本秒级时间计算，库存 P95 下界 855 ms，最终版库存 P95 上界 20 ms。最终版 40 RPS 的补偿候选 0 条，库存 Kafka Lag 峰值 1 条。本轮合并了实时投递、重试和资源变更，且数据库历史体量在各轮间增长。
- V5 分片版同机短测完成 149.1 笔/秒，HTTP P99 751 ms，使用独立 V5 schema 和历史扫描方式。V5 与中间版本的样本环境和负载形态存在差异，无法严格量化单项改造收益。
- 持续 120 · 关在 195.0 秒窗口完成 120.0 笔/秒，HTTP P99 301 ms，库存 P95 上界 1,238 ms，排空 0.4 秒，通过稳定性门槛。
- 本机最高通过的不限流候选为 120.0 RPS。更高档位或生产容量以单独长测为准。
- 350 档实际输入 349.7 RPS，完成抽奖 100.0 RPS，429 71.4%。这是开启保护时的突发测试。

最终复测活动产生 43,443 笔中奖订单和同量账本。隔离库合计 236,728 条已消费参与与同量额度扣减，236,328 笔订单与账本逐笔一致，190 个奖品库存与 MySQL 余额一致。负额度、负库存、重复订单、重复参与订单和未结算均为 0。重启演练中，应用就绪后约 2.66 秒达到三项终态，两组 Kafka Lag 归零。

## 部署边界

现有库切换使用停写、备份和迁移演练流程。正式入口需提供可信 Servlet Principal。单实例实测覆盖真实 Broker、数据库与 Redis，生产资源、真实发奖渠道和多实例高可用另行验收。Redis 预扣后 TX2 提交前退出或提交结果未知仍需对账。若持续超过实测容量，先核对 MySQL 提交与状态写入、库存热行锁和 Outbox 待投递，再决定资源配置。
