# Lottery 单库、限流与实时 Outbox 实测

> 本报告记录 V7 单库八表历史性能。V8 七表与本轮验证见 [活动独立奖池](activity-prize-pool.md)。

2026-11-11 至 11-12，Asia/Shanghai。JMeter 5.6.3 和应用运行在同一台 10 核、16 GiB 的 Apple Silicon 主机。独立 Docker 栈使用 MySQL 8.0.46、Redis 7.2.16 和 Kafka 2.8.1，MySQL 限 2 CPU/2 GiB。应用和 JMeter 使用 JDK 17，交付 WAR 使用 Java 8 构建。V7 压测复用了隔离库和原中间件资源配置，每轮使用新的活动、用户和库存。

## 改造与验证

- 八张业务表共用一个 MySQL 库和一个 Hikari 池。V6 旁路复制为分片自增 ID 重新编号，保留请求号、参与号、订单号和历史账本。真实 MySQL 验证跨片订单、请求和归属冲突回滚。V7 在隔离库保留了 159,917 笔既有订单。 [单库部署与迁移](single-database.md)
- HTTP 以 Servlet Principal 匹配请求用户，先获取本机许可，再用 Redis Lua 同时检查全局与用户活动令牌桶。默认全局 100 RPS、突发 32，每用户活动 2 RPS、突发 3，本机并发 24。429 分别标识全局、用户和并发拒绝，准入 Redis 故障返回 503。相同请求号经准入后可回放原结果。 [HTTP 契约](../.trellis/spec/backend/http-contract.md)
- Spring 三个独立固定延迟任务默认每 10 秒运行，活动只扫描到期状态。TX2 提交后把库存义务交给有界工作池。库存账本与条件扣减仍同事务，库存完成时持久登记发奖义务。两种消息独立记录重试时间与代数，发送失败退避，发送超时或进程退出按租期恢复，迟到回调无法覆盖新代数或终态。 [V7、重试与对账](outbox-delivery.md)
- 移除了库存和发奖的固定值 Redis 标记。HTTP 短锁继续使用所有者令牌，真实 Redis 验证旧执行者不能清除新标记。发奖事实与消息终态由同一条 CAS SQL 写入，BLOCKED 经人工对账后递增代数再释放。计划发奖字段保留历史快照与回放语义。
- Java 8 构建通过，默认测试 52 项。完整独立中间件回归 77 项；补充事务回滚和 Redis 所有权验证后复跑 32 项；最终调参后复跑 41 项，均无失败或跳过。覆盖同请求回放、并发扣次、库存预扣、账本幂等、Kafka 停机重启、消费者重新分配、回调代数、BLOCKED 恢复和索引扫描。
- 独立进程在 TX2 提交后、Kafka 发送前收到 SIGKILL，停机前库存投递代数为 0，账本不存在。重启后实际 Spring 调度恢复三项终态，账本一条，重放同一订单，个人额度只扣一次。活动从 PASS 自动启动、预热并到期关闭。

### 复现与根因

- **重复领取写入可直接复现。** 旧短测中，单库中间版 15,659 次显式 COMMIT 平均 2.18 ms，历史最终版 15,613 次平均 18.10 ms，两者均约每单 3 次，对应 TX1/TX2/TX3。实时版库存和发奖都在原事务或状态写入后追加一次独立领取 UPDATE，另外还有两个 Broker 结果 CAS。中间版原有发送状态写入，直接新增的领取写入通常为每单两次。MySQL 的 COMMIT Digest 仅统计显式提交，独立 UPDATE 的 autocommit 成本计入各自语句。实时版还将模拟发奖事实与消息终态合并为一次写入，并减少一次订单快照读取，所以不能把所有实时版写入视为净新增。
- **零换页也能复现长测失败。** 同一未修改版本 150 短测 P99 为 31 ms，停压库存积压为 0。301 秒基线约在第 225 秒出现持续资源拒绝，最终拒绝 1,045 次，Hikari 活跃/等待峰值为 48/9。库存 Kafka Lag 峰值 50，停压时 Kafka Lag 已是 0，但仍有 153 笔库存义务待投递。首尾平均发奖积压增长 215.57 单，排空 15.28 秒，分别违反原有增长及 15 秒门槛。历史最慢轮也在 Kafka Lag 下降后继续按约每 10 秒 96 单排空，吻合默认每轮 3 批、最多 32 个补偿许可。运行中的容量拒绝把实时义务转为到期扫描，因此即使 HTTP 成功，尾部仍会跨多个补偿周期。
- **锁等待和持久日志 I/O 同时存在。** 基线长测记录 44,910 次 InnoDB 行锁等待、累计 105.95 秒；采样可见 `draw_order.uk_order_id` 的状态写入竞争和 `draw_config_prize.idx_draw_config_award` 的五个奖品热行。实际执行树显示两个补偿查询按各自到期索引作范围扫描，空扫描读 0 行。关键 UPDATE 计划按唯一订单、用户活动和奖品组合键各定位 1 行。基线长测两种首发领取共 92,228 次，Digest 累计 352.06 秒，其中语句锁列共 0.55 秒。该锁列不能代替 InnoDB 逐行等待统计，累计时间会重叠。
- 基线后段两个事务阶段均值明显增加，TX1 从 3.79 升至 24.69 ms，TX2 从 3.45 升至 19.40 ms；库存和发奖 Kafka 位点提交均值只从 0.87/0.77 升至 1.18/1.07 ms。持久日志文件的 `MISC` 计时在积压出现附近升高，抽样区间 InnoDB 日志/binlog 每次均值从 0.69/0.85 升至 1.49/1.89 ms，数据文件 fsync 约从 1,244 降至 671 次/秒。MySQL 配额在该采样段无新增 throttling，`Innodb_log_waits` 为 0，Kafka 容器有间歇 CPU throttling。日志 I/O、事务竞争与等待放大符合观察到的退化；`MISC` 包含多种操作，现有采样无法把历史 18.10 ms COMMIT 拆成精确的 fsync、锁和调度比例，也未进行 Kafka 原生镜像单变量实验。 [MySQL 持久化与二进制日志](https://dev.mysql.com/doc/refman/8.0/en/binary-log.html)
- 初版实时短测测量窗口零换页时已经积压，完整观察仅 1.61/0 MiB，仍排空超标，本轮长测在 0/0 MiB 下仍失败。历史最终版严重退化伴随换页和较高 MySQL CPU，换页可能放大延迟，但现有轮次无法估计其独立贡献。单库中间版长测已失败，证明持续容量问题早于实时 Outbox。当前实验证明了实时首发的写入放大以及共享工作池、补偿速率对积压的放大机制。

### 优化

TX2 在写入库存义务时同时登记首发代数。库存终态 CAS 在写入发奖义务时同步递增发奖代数，仅状态推进成功的消费者安排首发。实时线程直接使用已登记的代数发送，每笔正常中奖省去两个独立领取 UPDATE。两秒补偿资格、到期领取的 45 秒租期、迟到回调保护及消费者幂等均保留。首发在补偿到期后仍在途时可能重复发送，旧代数回调无法覆盖新领取，唯一账本和发奖 CAS 保证业务事实只推进一次。单库、TX1/TX2/TX3、Kafka 消息协议及 MySQL 持久化配置沿用原实现。无需新增迁移，连接池、工作池、限流及验收阈值沿用原设置。

### 容量、过载和正确性

- 40 RPS 反向对照和复跑同用 20 线程、8 秒预热、30 秒运行。A 的 HTTP P95/P99 为 12/16 ms，库存为 9/15 ms。B 首轮为 14/17 ms、10/42 ms，库存长尾集中在两个短时段。两轮间保留中间件运行，再用相同参数复跑 B，HTTP 为 13/17 ms，库存为 8/12 ms。三轮均无 Outbox 拒绝，约 0.3 秒确认排空。首次尾部波动保留在证据中。
- 优化版 120 RPS 持续 195 秒完成 119.95 笔抽奖/秒。HTTP P95/P99 为 88/312 ms，库存 P95/P99 上界为 463/809 ms，发奖为 486/840 ms。停压时库存与发奖待处理均为 0，0.28 秒确认排空，原稳定性门槛全部通过。
- 开启默认限流的 350 RPS 突发，实际输入 349.83 RPS，抽奖完成 100.02 RPS。测量窗口有 5,474 个 429（71.4%），系统错误为 0，准入抽奖 HTTP P95/P99 为 20/26 ms。库存 P95/P99 上界为 26/260 ms，Hikari 活跃/等待峰值为 4/0，Outbox 容量拒绝为 0，停压后 0.22 秒排空。逐单审计核实限流请求没有创建参与记录。
- 150 RPS 是本轮最高实际通过的不限流持续档位，实测 149.87 RPS、301 秒，完成库存结算和模拟发奖。末段短时出现连接等待和 Kafka Lag，当前结果覆盖这次负载与宿主机条件。
- Java 8 `mvn -o clean package` 通过 53 项默认测试，另外通过 80 项真实中间件及 SQL 集成测试。覆盖生产 Mapper 的补偿代数竞争、迟到回调、真实 Kafka 停机重启、事务回滚和发奖幂等。首次归属测试因和 V4 用例共用同名 fixture 库而在建库时失败，独立空库复跑 10 项通过。独立 E2E 使用本轮新建 MySQL，原隔离数据保留。
