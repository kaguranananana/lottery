# 活动独立奖池与 V8 切换

一个活动有一个奖池。活动编号是抽奖、Redis 预扣与 MySQL 结算共同使用的业务编号。同一目录奖品可以进入多个活动，每个活动单独配置概率和库存。

| 表 | 主要数据和关系 | 关键约束 |
|---|---|---|
| `activity` | 活动号、名称、时间、状态、个人次数 | 活动号唯一；状态保持 1/4/5/7；开始和结束分别按状态、到期时间扫描 |
| `activity_prize` | 活动号、奖品号、概率、初始和剩余库存 | 活动与奖品外键；组合唯一；概率 0–1（六位小数），剩余库存介于 0 和初始库存 |
| `award` | 奖品号、类型、名称、内容 | 奖品号唯一，可由多个活动引用 |
| `user_activity_quota` | 用户在活动中的初始额度与剩余次数 | 用户和活动组合唯一 |
| `draw_participation` | 参与号、用户、活动、原请求号、参与时间、消费状态 | 参与号唯一；用户/活动/请求唯一；同一用户活动最多一条未消费记录 |
| `draw_order` | 订单号、参与号、用户、活动、奖品快照、结算和发奖事实、Outbox | 订单号、非空参与号、历史 UUID 各自唯一；库存、发奖分别按重试时间和订单号扫描 |
| `award_stock_settlement` | 订单号、用户、活动号、奖品号、结算时间 | 订单号唯一；账本插入与库存条件扣减同事务 |

`draw_config`、各处的 `draw_config_id`、配置描述和历史发奖方式/计划时间从在线模型移除。实际的 `fulfilled_at`、奖品快照、库存终态时间、重试时间和代数继续使用。HTTP 的 `award.grantType` 移除；`award.grantDate` 字段名保留，内容只表示实际完成时间（完成前为 null）。旧计划时间仍可在选择保留的只读 V7 源中按订单号查到。中奖回放仍用原参与号和订单号、下单时的奖品快照。

生命周期只保留 DRAFT(1)、READY(4)、RUNNING(5)、CLOSED(7)。DRAFT 可转 READY；READY 可启动或关闭；RUNNING 可关闭。活动行锁内检查 READY 和时间窗口，以 SETNX 预热，再 CAS 发布 RUNNING。启动失败保持 READY，下一次可补齐未初始化的键。RUNNING/CLOSED 禁止从 MySQL 自动补键；缺键抽奖失败，保留原请求用于对账后重试。快照缓存使用新命名空间并在配置事务提交后失效。

TX1 仍在同一事务扣个人机会并创建参与记录。TX2 仍在同一事务消费参与记录并创建订单和库存 Outbox；已确认回滚按活动和奖品回补 Redis。TX3 插入唯一账本并条件扣减该活动奖品库存；不足回滚账本并进入 BLOCKED。先完成库存才登记发奖义务。实时投递、定时补偿、回调代数 CAS 和模拟发奖终态沿用原实现。

## 从空库部署

用 `lottery-schema.sql` 建库；可用 `lottery-demo-seed.sql` 构造独立奖池。该种子仅适用于空库。使用新 Redis 和 Kafka 实例或专用命名空间，旧库与卷可以原样保留。这是本轮实际采用的回归方式。

## 需要保留旧业务数据时

V8 是旁路迁移。已有分片数据先走 V5、V6 和 V7 的既有流程；V6 使用冻结的 `lottery-v7-schema.sql` 并回填 V7 字段；经 V6 工具生成的库无需再重复执行 V7。V8 不支持新旧应用同时写入。

1. 做 MySQL 与 Redis 备份，先在隔离还原库演练。停止对旧应用的入口写入，等待正在运行的抽奖结束。用旧应用排空库存和发奖 Outbox，核对两个 Kafka 消费组所有分区 lag 为 0，确认无 BLOCKED，再停止旧应用和其它生产者。
2. 生成审计和迁移 SQL。以 MySQL 批处理执行，禁止 `--force`。审计输出冲突类型、总数和最多 100 条身份，发现冲突时在建目标库前退出。共享奖池必须先由业务确定库存与历史归属，不能直接复制余额。合法且未下单的未完成请求可保留；不明确的请求归属须先处理。

   ```sh
   python3 docs/sql/V8__activity_prize.py --source lottery --audit-only > v8-audit.sql
   python3 docs/sql/V8__activity_prize.py --source lottery --target lottery_v8 > v8-migrate.sql
   mysql --batch --default-character-set=utf8mb4 < v8-audit.sql
   mysql --batch --default-character-set=utf8mb4 < v8-migrate.sql
   ```

3. 对比目标表结构和迁移输出。七张表保留字段按行核对。账本的活动号来自原订单，奖池活动号来自审计通过的一对一映射。DDL 先建目标结构；后续 DML 用独立事务，失败会回滚复制数据，已建结构留供诊断。重跑选新的目标库。
4. 核对旧 Redis 和 MySQL 库存。可用 `copy_v8_stock.py --source lottery --mysql <连接旧库的可执行包装> --redis <连接旧Redis的可执行包装>`，通过后加 `--apply`。停写时只复制余额一致的现有键，不覆盖目标键，不清理旧键。运行中或仍有未完成参与的活动缺旧键时中止；对账完成后才能切换。已关闭且无未完成参与的活动可以没有库存键。
5. 新应用使用目标库、原 Kafka topic 与消费组（保留位点），并使用新的库存和快照键。两个消费者均按用户和订单号查询持久订单：旧库存消息的 `strategyId` 会被忽略，绝不当成活动号；新库存消息的 `activityId` 仅供观测，扣减仍由订单决定。旧发奖消息中的计划字段也不参与执行。迟到的完成订单消息不会重新扣减。
6. 开放写入前，用只读请求检查目标数据、缓存和消息状态。目标开始接受写入后，不能直接切回旧库，否则会丢掉切换后的订单和库存变更。

已知边界：Redis 预扣后、TX2 提交前的进程退出仍需对账；事务结果未知或 Redis 回补失败需要人工介入。当前发奖处理器仍为本地模拟渠道。

## 回归复现

- Java 8：`mvn -o clean package`。
- 独立 MySQL/Redis/Kafka：用 `mq-e2e/docker-compose.yml` 启动新项目，测试命令传 `-Dlottery.e2e.project=<Compose 项目名>` 和 `-Dlottery.it.redis.port=16379`，运行 `FinalBusinessE2eManualIT,MqMiddlewareE2eManualIT,RedisStockFailureManualIT,DrawAdmissionRedisManualIT`。测试会在核验专用容器身份后重建自己的库。
- V8：在另一独立 MySQL 上运行 `verify_v8_migration.py --mysql <专用 mysql 包装> --suffix <新后缀>`。使用交叉编号的 V7 样例，检查共享奖池、重复奖品、未排空 Outbox 均在建库前阻断。通过场景核对七表的完整结构、余额、账本、历史标识和实际发奖时间。
- 压测复用 [JMeter 与 PerfHarness](../doc/performance/README.md)；V7 历史工具与 V8 新模型分开运行。每轮使用新的活动和用户，结束后必须核对参与、订单、账本、次数及两套库存。

## 2026-11-13 实测

V7 基线为 `4ab32e5`，两版使用同一个专用 Docker 栈、不同的空业务库，每轮新建活动与 65,000 名用户。MySQL 8.0.46 保持持久化 1/1、限制 2 CPU/2 GiB；JMeter 5.6.3 用 72 个线程，前 10 秒剔除。40/80 为 75 秒短测，120 为 195 秒，150 为 301 秒。奖池五种等概率奖品，总中奖率 100%。压测与现场记录未使用现有演示库写数据。

| 目标 RPS | 实际 HTTP RPS V7 → V8 | HTTP P50/P95/P99，ms | 库存 P95/P99 上界，ms | 模拟发奖 P95/P99 上界，ms | 排空秒数 |
|---:|---:|---|---|---|---:|
| 40 | 40.02 → 39.97 | 10/59/188 → 10/40/170 | 79/302 → 32/120 | 103/332 → 45/146 | 0.15 → 0.34 |
| 80 | 79.98 → 80.00 | 11/32/209 → 19/70/217 | 40/455 → 141/432 | 53/488 → 165/452 | 0.17 → 0.17 |
| 120 | 120.02 → 119.98 | 27/270/880 → 27/432/827 | 18,367/45,873 → 21,989/36,946 | 18,437/45,881 → 22,050/36,955 | 19.51 → 24.88 |
| 150 | 150.75 → 150.02 | 33/345/749 → 47/193/439 | 74,863/104,182 → 93,849/101,400 | 74,887/104,208 → 93,857/101,408 | 76.83 → 73.13 |

不限流四档两版业务和 HTTP 错误率均为 0。V7 四轮共 77,545 单、V8 共 77,670 单，各自逐单匹配参与、扣次、订单和账本；Redis 与 MySQL 余额逐奖品一致，最终无 BLOCKED、两组 Kafka Lag 为 0。上界使用订单 INSERT 到完成时间，提交发生在 INSERT 与 HTTP 返回之间；原稳定性门槛仍使用既有保守算法，没有改阈值。

120、150 RPS 两版均未通过持续稳定性门槛；40、80 是短测，不能认证持续容量。150 RPS 的 V8 入口 P99 更低，但停压待库存结算由 8,523 增至 13,037，库存组采样峰值 Lag 由 7,875 增至 13,051，测量窗内消费组位点推进约 125.8 → 104.3/s。发奖组峰值 Lag 仅 10 → 16，说明主要积压位于库存消费者。150 RPS 的阶段均值 TX1/TX2/TX3 分别为 37.80/33.31/14.47 → 29.00/26.15/16.30 ms。两个版本都观察到奖品库存热行上的锁等待，V8 的该 UPDATE 仍按组合唯一键访问估算一行，补偿扫描使用原重试索引。MySQL 平均 CPU（单核为 100%）110.8% → 131.9%，Hikari 活跃峰值均为 48，等待峰值 38 → 36，无获取超时。负载窗采样中的 InnoDB 行锁累计等待约 197 → 350 秒；包含多事务并行等待。JVM GC 累计 182 → 126 ms，堆峰值约 351 → 355 MiB；GC 不是这次长积压的主要证据。

两轮 150 RPS 都发生大量换页，V7 约换入/出 1,871/1,916 MiB，V8 约 1,467/905 MiB；中间件和宿主背景也不同。结果显示异步 P95 和高负载积压有退化，无法从一次顺序测量把变化归因于表重构，也无法据此通过「无明显退化」验收。后续应在低换页、隔离的宿主上交替跑 V7/V8，同步核对 TX3、库存热行和持久提交耗时；优先保持准入保护。

SQL 计数口径：V7 150 RPS 的服务器摘要含 134,253 次 COMMIT，累计 1,947 s、均值 14.50 ms；旧库存 UPDATE 44,944 次、累计 58.98 s、均值 1.31 ms。V8 长测的临时双库配置初次未同步服务器摘要的 schema 筛选，不能把其零增量解读为无 SQL。V8 分档的生产 Mapper 计时和真实执行计划独立可用；新库累计服务器摘要及修正筛选后的限流轮单独记录，不能冒充逐档 COMMIT 对照。Redis 延迟监视只保留 LATENCY 事件和准入 Lua 计时，不从它推算每次库存命令的 P95/P99。

迁移样例实测：旧订单 91 和参与 81 回放原奖品快照及实际发奖时间；请求 82 只允许原请求继续，额度未再扣。活动 502 新增一笔结算后库存 4 → 3，活动 501 的同一奖品仍为 7。首次手工构造时客户端字符集错误已在写入 V7 样例时复现，修正 UTF-8 客户端后重新建样例并完成 HTTP 核对。真实故障复演在 TX2 提交且首发未入队时杀进程，重启后 Spring 调度按第二代发送；HTTP 就绪后约 0.41 秒达到三个终态。原请求返回原订单、只扣一次额度、只有一条账本。独立的 150 组新请求与同号回放各去掉前 20 个样本；单线程样本的 HTTP P50/P95/P99 分别为 23/29/37 与 7/10/11 ms，只有 150 条参与和订单。

默认限流复验：约 349.47 RPS 输入，HTTP 完成 349.72 RPS，其中新抽奖 100.09 RPS。测量窗内 2,452 次中奖、6,109 次全局限流、6 次本机并发限流；无系统错误，拒绝请求无参与记录。停压有 68 笔库存待处理，2.54 秒排空；全轮 3,395 笔订单和账本逐单一致。Redis 准入 Lua 平均 3.11 ms。该轮 V8 服务器摘要为 10,061 次 COMMIT、累计 128.69 s、均值 12.79 ms。限流短测和不限流长测负载不同，不能直接用两者的提交延迟计算优化幅度。

实测摘要见 [activity-prize-20261113.json](validation/activity-prize-20261113.json)，索引命中见 [执行计划](validation/activity-prize-plans-20261113.txt)。逐请求 JTL、SQL、分区位点和逐订单对账文件留在本机隔离压测会话中，历史原始结果未改写。150 RPS 下库存 Mapper 计时约 45,015 次、累计 97.29 s、均值 2.16 ms → 45,141 次、累计 114.93 s、均值 2.55 ms（包括 JDBC 往返）；对应库存消费者 ACK 均值 2.61 → 2.86 ms。V8 150 RPS 的库存 UPDATE 与发奖 CAS 没有变成全表扫描。以每次写入的持久提交和热行等待定位瓶颈，比继续缩短 HTTP 入口更有价值。

低换页复核：同一隔离栈顺序执行 90 秒、目标 150 RPS 的两轮，前 10 秒剔除；V7/V8 分别换入 3.30/2.42 MiB，均无换出。HTTP 完成 150.04/150.09 RPS、P99 195/183 ms，13,467/13,433 笔订单全部结算并逐笔对账。V8 在停压时库存待处理 3,818（V7 为 3,382），库存 P95/P99 上界 33.30/35.58 秒（V7 为 29.11/31.25 秒），排空 20.32 秒（V7 为 15.89 秒）。这里两版 SQL 摘要按正确业务库采样：COMMIT 39,936/39,797 次、累计 399.62/432.49 秒、均值 10.01/10.87 ms；库存 UPDATE 13,416/13,394 次、累计 17.08/19.23 秒、均值 1.27/1.44 ms。低换页条件下仍观察到 V8 的异步尾延迟回退，不能把长测差异全部归因于换页。此轮是复核，不替代持续容量门槛。

测试结果：Java 8 默认 53 项，真实 SQL 34 项、HTTP E2E 28 项、Redis 10 项、Kafka 9 项。Kafka 复跑曾在 Docker 健康探针等待阶段超时，按实测调整测试容器的探针窗口后定向通过；生产参数、用例断言保持不变。现有业务库未做迁移或切换。迁移工具还在样例目标接受新写入后检测到 Redis 余额差异，并明确拒绝重新复制。
