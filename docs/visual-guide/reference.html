三个 ID 串起一次业务

事务到哪里结束

事务库 / 操作一起保证不在事务内
TX1 · 参与按uId选同一个用户库；必要时初始化次数，条件次数-1，INSERT take。次数与参与记录共同提交 / 回滚。之前的Redis活动DECR；失败回补是独立操作。
TX2 · 中奖订单同用户库；CAS take 0→1，INSERT user_strategy_export_000..003。消费参与机会与订单/库存Outbox共同提交。之前的Redis奖品DECR；以后Kafka发送。
TX3 · 奖品结算全局db00；INSERT award_stock_settlement(order_id唯一) + 条件扣strategy_detail。同一个orderId的持久库存只成功扣一次。用户分片stock状态；发送invoice；两个topic位点。
独立状态UPDATE用户库的stock/mq CAS、发奖grant CAS；未中奖consumeTake为单条CAS。每条SQL原子决定是否推进，终态不被迟到回调覆盖。没有包住Redis、两种MySQL库与Kafka的分布式大事务。

数据库同库事务解决局部原子性；Outbox保存未完成责任；消息重放和唯一账本把局部提交衔接起来。

三列状态，各自证明一件事

列值当前事实与推进条件
stock_mq_state0 INIT / 3 SENT / 1 COMPLETE / 2 FAIL / 4 BLOCKED0订单创建；3发送成功；1消费者结算成功；2投递失败可重试；4库存条件扣减分歧，持久等待对账。发送成功只0/2→3，失败只0→2，消费成功0/2/3/4→1。
mq_state0 INIT / 3 SENT / 1 COMPLETE / 2 FAIL发奖消息状态。只有本地grant=1才允许0/2/3→1。补偿发送成功写3；旧文档中补偿写1的行为已修正。
grant_state0 INIT → 1 COMPLETE当前模拟handler执行本地CAS。枚举还有2 FAIL，但这条主链路没有写2的逻辑；消费异常通过抛出和不ack恢复。

当前补偿：库存扫0/2和超10分钟的3；发奖需stock=1且grant!=1，扫FAIL、创建超30分钟的INIT、更新超10分钟的SENT，另包含已证实的历史mq=1但grant未完成数据。BLOCKED被Job扫描排除，人工处理流程是核实修复后按原订单CAS 4→0；当前没有自动对账任务。消费者不以BLOCKED早退，已在Kafka中的重复消息仍可进入结算；若已恢复扣减条件，成功消费允许4→1。

源码：UserStrategyExport_Mapper.xml。两个阶段共用订单update_time，超时依据不是独立的消息时间列。

当前实现与历史材料的区别

  • 当前入口是HTTP LotteryController。refactor-audit.md是重构前审计，其Dubbo入口、规则树、旧算法、旧活动Kafka链路、Scheduled dispatcher和无账本结算不属于现行主链路。
  • V2 SQL对参与表后缀和request_id全表唯一的注释属于旧形态；当前DAO参与只分库，V3迁移建立用户/活动/请求号组合唯一与未完成记录唯一。
  • XXL-Job已经注册三类Handler，实际调度配置仍需部署环境提供；不能把旧“每5秒Scheduled扫描”画成现在的触发计划。
  • 四种发奖handler均为adapter stub。完成只意味着当前本地模拟逻辑落库；真实券平台、物流与第三方交付未接入。
  • 活动关闭没有自动回写Redis剩余库存；运行期库存丢失也没有自动对账程序。手工恢复节点是运维边界。
  • 明确下单业务失败会回补奖品库存；下单直接抛异常未进入这一回补分支。库存回补失败当前只记error，没有保证补偿必达；不画成全面自动恢复。
  • 本地Kafka配置acks=1、replicas=1；图中的重放与补偿为源码能力，不宣称生产环境无条件可靠、无限重试或外部效果恰好一次。

试着独立讲清楚

为什么中奖响应可以先于发奖？

TX2已把订单和库存Outbox责任一起提交。响应只报告中奖；Job发现责任，Kafka触发账本结算，再发invoice，本地handler与消息状态最后收口。

为什么同时需要requestId、takeId和orderId？

requestId关联同一个逻辑请求的重试；takeId关联消耗的一次参与机会；orderId关联中奖后结算和发奖。未中奖有take，却没有中奖订单。

扣库存成功后宕机，重放为什么不会再扣？

账本与strategy_detail扣减在同一个db00事务中。已提交的orderId重放INSERT撞唯一键，因此跳过扣减，继续补齐用户订单状态。

为何运行期Redis库存丢失不能直接从MySQL恢复？

奖品MySQL结算可能滞后，活动MySQL没有随每次参与扣减。直接覆盖实时库存会把已经消耗的部分重新上架；当前需要人工核实，启动预热只允许PASS。

SENT、COMPLETE和grant_state=1有什么区别？

SENT只是消息发送成功；库存COMPLETE表示结算完成；grant_state=1表示本地模拟发奖事实；发奖mq_state=1需grant已完成后消费者确认。

什么时候可以说整个流程完成？

未中奖：take已消费并返回D001即可。中奖：同步先返回O1；本地异步需账本存在、stock=1、grant=1、mq=1以及两个消费位点确认。真实外部交付尚未实现。
