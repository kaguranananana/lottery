# 实验方案与改动边界

当前差距是最高持续能力未确认，补偿 SQL 对已发奖历史订单仍全量过滤。问题位于订单分片查询访问路径，不在消费者线程数或业务状态协议。

先使用 preflight 观察约 60 秒；核对 Docker 项目/service/本机端口、资源限制、挂载及状态，只恢复旧专用四容器。JDK17/JMeter5.6.3、原堆/池/并发/调度/数据库持久参数不变。构建与测试串行，应用就绪后再次预检。只有资源可信才开始测量；活跃换页与竞争明显时停止无效容量搜索。

负载保持30线程、20秒预热、10万预置用户、五种各20%模拟券、全中奖，每轮新活动。原版80 RPS测量180秒；通过后逐级100/120等，不预设目标，候选至少180秒，最高通过候选300秒。每轮逐ID审计且排空才下一轮。数据库历史增量逐轮记录，禁止偷偷重置初始体量。

唯一预定候选是补偿访问路径：保留原 SQL 条件，评估以 grant_state 为前导列的最小非唯一索引。需当前八表实际 EXPLAIN ANALYZE 再确认。若值得实施，新增显式八表迁移及真实 Mapper 的扫描契约/计划测试；不改变 Java 消费者、回调、事务、ack 和持久化。索引增加插入/发奖状态更新维护成本，必须用同负载真实链路检验净影响。

局部 SQL 对照必须相同订单数据、相同谓词、多次交替计划，用仅在实验会话改变的索引可见性/索引选择说明因果。全链路采用独立活动并如实记录历史增长、顺序与资源；必要时反向重复。没有可靠对照则只认证读取工作量减少，不宣称总体提升倍数。DDL 只在专用库、应用停止且原义务排空时执行，回滚只移除本次新增非唯一索引，保留全部业务数据与既有索引。

正确性复用默认单测、真实 SQL 扫描测试、HTTP 幂等/超时/D007、真实 Kafka 重投与本轮全量审计。新测试只写专属 fixture schema，不 DROP 业务三库。资源不足时不扩展架构或配置，报告明确未执行项。
